## 3. 实施要求

1. **统一首次加载和返回刷新。** 首次进入的 `onLoad → onShow` 整体只查一次第一页。之后从新增或详情返回时刷新第一页。空列表、加载中、加载失败在界面上可区分。
2. **成功后再更新列表和页码。** 首次加载成功可显示空态；已有数据刷新时，先保留当前记录，待新第一页成功再整体替换。翻页失败保留前页内容，点击重试继续请求刚失败的页。保持当前每页 20 条以及按旧 `_id` 打开详情的行为。
3. **确保刷新与翻页按用户意图生效。** 同一次翻页过程中连续触底只产生一次请求。用户在翻页期间下拉刷新时，最终应看到最新第一页；过时请求的成功、报错、收尾都不能覆盖新结果或提前放开加载锁。可串行调度或识别过时请求，选择较简单且能通过测试的实现。
4. **让错误可恢复。** 首屏出错给出重试按钮。已有内容时，一处简短提示即可，重试动作要区分“刷新第一页”和“接着加载下一页”。下拉手势在成功或失败后均应结束。测试期间模拟网络出错后可以再次成功，避免只验证报错文字。

## 4. 验收用例

新增的测试应能用 `node --test tests/record-list.test.cjs` 单独执行。可以捕获原生 `Page(...)` 定义，给每个用例独立的 `data/setData`，替换数据库响应和所需的 `wx` 接口。注意 `utils/db.js` 在模块载入时就引用 `wx.cloud.database()`，模拟依赖应在加载页面前就绪。用手动控制的 Promise 制造延迟，不靠定时等待碰运气。

| 编号 | 触发步骤 | 必须观测到的结果 |
|---|---|---|
| L01 | 按次序触发首次 `onLoad`（若有）与 `onShow`，返回空数组 | 只请求一次 `(1, 20)`；加载结束，出现“还没有攀岩记录” |
| L02 | 返回一条旧记录，含 ID、日期、地点、难度、总尝试次数、备注及照片引用；点击卡片 | 保留这些字段，按原 ID 跳转现有详情页。旧总次数如实展示 |
| L03 | 从新增页回到列表，再次触发 `onShow`；最新第一页增加一条 | 新记录可见；以新第一页替换旧内容，同一条记录不会因刷新出现两次 |
| L04 | 首屏查询失败，触发页面绑定的重试操作，第二次成功 | 失败时显示可恢复的错误态；两次都请求第一页；重试后显示记录 |
| L05 | 当前已有记录，下拉刷新失败，再重试刷新成功 | 失败期间保留原记录；下拉动画结束；重试请求第一页，新数据替换旧数据。另覆盖下拉成功也结束动画 |
| L06 | 有 21 条固定测试记录：第一页 20 条，连续触底两次，第二页首次失败，再点重试 | 请求页码依次为 `1, 2, 2`；中间保留 20 条，最终 21 个不同 ID；再次触底无第 3 页请求 |
| L07 | 第二页尚在途中时下拉刷新，让旧第二页与新第一页按受控顺序完成 | 最终结果等于刷新后的第一页；旧第二页不会混进列表。再验证旧请求失败不会把刷新成功的界面变成错误态 |

L01–L07 都要给出离线测试结果。用测试验证页面状态和点击处理，另核对 WXML 的条件分支与事件名确实绑定到对应方法。能使用微信开发者工具和独立测试环境时，再从底部“记录”实际走一遍首次进入、打开详情、返回和下拉。缺少测试环境时，写明哪一步待验和复测方法，继续完成离线工作。请勿为制造空集合或分页样例去清空、写入真实个人数据。
