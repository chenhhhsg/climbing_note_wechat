# 攀笔微信小程序改造计划 v0.2

2026-11-05 · 适用仓库 `climbing_note_wechat` · 代码基线 `5249ee4` · 待实施

**项目目标**是在岩馆休息的几十秒里记下一次尝试，下次回到同一条线时能找到此前的动作、体感和视频。首版面向室内抱石，以现有原生微信小程序为客户端。先交付可以独立使用的训练日志，再让用户从某一次尝试发起视频复盘。

第一次在岩馆验收时，用这样一段经历走完整个流程：周四新建“蓝色动态线”，连续记两次失败，给第二次补一句“抓到后向右摆”；周日从历史线路进入，记下第一次完成。线路页应列出两天的三次尝试，日历应显示两次实际训练。只有第二次有视频也能成立。接入分析后，从那次尝试打开报告，点一条观察，就能回到发生摆荡的那几秒。

## 1. 工程起点与技术决策

工作区有两个同级目录。本文中的源码路径均以 **`climbing_note_wechat/`** 为根。

| 位置 | 当前内容 | 本轮用途 |
|---|---|---|
| 本仓库根目录 | `app.js/json/wxss`、微信项目配置、六个原生页面、`utils/`、图标 | 在此迭代 JS、WXML、WXSS，沿用原有页面入口和组件样式 |
| 同级 `climb_coach_blueprint_v0.1/climb_coach_blueprint/` | 产品及 API 文档、平台接口定义、报告 Schema、虚构报告样例、Python 领域规则与测试 | 采用跨天线路、逐次尝试、任务状态、时间轴和报告校验规则。实施时将实际采用的契约及对应测试纳入版本控制，避免依赖开发机上的同级目录 |
| 工作区根目录的《攀岩项目_源码审查与初步方案_v0.1》 | 对三个参考项目的审查与初步架构 | 保留作设计依据。其 uni-app x 选型验证调整为现有微信前端的真机媒体验证 |

**建议的工程取舍。** M0 先验证现有微信云开发环境。若账号、私有访问规则和测试环境可用，M1 沿用云数据库作为训练记录的唯一写入位置，由云函数验证身份、关联关系和重复提交。这样能先验证岩馆里的录入体验。若云环境无法使用，或计划近期让独立 App 共用账号和记录，则在 M1 建表前改走蓝图的 FastAPI + PostgreSQL，由同一套页面调用业务接口。两条路线择一实施；已有数据另行核对后迁移。

**视频分析单独部署。** 保留蓝图的独立 Python worker 设计。若 M1 走云开发，M2 由云函数建立持久任务，worker 通过受限的服务端接口领取、续租、写回；页面按任务 ID 查询。若走 FastAPI，这些操作由 API 和数据库承接。Python 依赖、模型权重、密钥都放在服务端工程。当前微信项目以仓库根目录作为小程序源码目录，将来同仓放置服务端时，先明确分包目录和上传排除规则，并检查开发者工具的上传文件清单。

## 2. 现有文件如何改

| 现有位置 | 源码现状 | 拟改动 |
|---|---|---|
| `app.js`、`project.config.json` | 已配置小程序 AppID；云环境仍为 `your-env-id`。配置声明了云函数目录，本地尚无对应实现 | 核对 AppID 所属项目与开发环境；区分开发数据和已有个人数据；给云服务初始化失败提供可读提示 |
| `app.json`、`app.wxss`、`images/` | 四个底部入口为首页、记录、统计、我的 | M1 在首页加入日历和当日场次，从记录页进入线路。M2 有实际报告后再增加复盘入口；统计可从日历进入 |
| `pages/index/` | 最近五条记录、添加按钮 | 首页按选中日期显示计划和实际训练；开场后优先显示“继续本场”，让用户回到正在练的线路 |
| `pages/add-record/`、`utils/grade.js` | 每次提交都填写日期、地点、类型、难度，输入总次数，照片先上传再保存记录 | 场次承担时间、岩馆；线路承担难度、颜色、照片。选好线路后，点一次结果即保存一次尝试，备注、体感和视频可稍后补。抱石沿用 V 级，增加岩馆色标或自定义标签 |
| `pages/record-list/`、`pages/record-detail/` | 按日期列出旧记录，详情按旧记录 ID 加载、预览照片和删除 | 先修首次加载；旧 ID 继续打开历史详情。增加线路列表与线路详情入口，按场次分组展示逐次尝试，避免把旧 ID 当线路 ID |
| `pages/stats/`、`utils/date.js` | 总次数取 `records.length`；`getAllRecords()` 只发一次查询；最高难度遍历所有记录 | 分开统计实际场次、逐次尝试和完成的不同线路；按用户本地日期归档；最高完成难度仅在同一难度体系内比较。使用聚合或完整分页 |
| `pages/profile/` | 个人资料、缓存、反馈等入口；“清除缓存”调用 `wx.clearStorage` | 增加导出、删除和视频保留设置。存在待同步尝试时保护草稿；云端所有权由服务端身份确定 |
| `utils/db.js` | 集中直接访问 `climbing_records` 和云存储，图片上传路径固定为 JPG | 保留旧记录读取入口；将新业务操作集中到拟新增的 `services/training.js`，媒体操作放入 `services/media.js`。页面只传业务 ID，测试时可替换数据来源 |

**页面拆分建议。** 在 `pages/session-detail/` 放“本场线路”和“再记一次”，在 `pages/route-detail/` 放跨天历史。复盘阶段再新增 `pages/analysis-detail/`，通过 `app.json` 注册。旧表单的选择器、缩略图和日期展示可就地提取复用；第一轮不需要重排整个项目目录。

## 3. 新记录怎样保存，旧记录怎样读

| 数据 | 最小关系与规则 |
|---|---|
| 计划、场次 | 一次实际到馆训练对应一个 `Session`。计划可关联后来完成的场次；仅保存计划不会增加实际训练次数。同一天允许有多场 |
| 线路 | 一条 `Route` 有稳定 ID、岩馆、名称或描述、难度标签、可选照片。同一岩馆可以有两条相同颜色和难度的线。岩馆换线时归档旧线，新线另建 |
| 当天练的线路 | `SessionRoute` 关联一个场次和一条长期线路，同一场次反复选择同一线路返回原关联 |
| 尝试 | 每次点击结果创建一个 `Attempt`，关联 `SessionRoute`，保存结果、时间、可选体感与备注。发起请求前生成操作 ID；同一操作重试复用该 ID，下一次真实尝试使用新 ID。服务端按用户和操作 ID 去重 |
| 媒体与报告 | 线路照片帮助辨认线路；一次尝试的视频归属该 `Attempt`。同一视频可按不同问题创建分析任务，每个任务保存独立报告和版本。用户能补充或纠正观察，原始体感由用户维护 |

**旧数据默认按原文保留。** 首先在有权限的环境确认是否存在真实 `climbing_records`，记录总数、图片引用数并做可恢复的备份。若存在，旧列表继续显示原日期、地点、难度、`attempts`、状态、备注和照片。比如“V3，尝试 5 次，完成”只能支持一次汇总，无法还原五次各自的结果。允许用户手动关联到一条线路，以“历史汇总”展示；跨日同色同难度的记录也由用户确认归属。若集合为空，直接启用新记录流程。

**切换与核对。** 在测试环境演练，核对旧 ID、条数、图片可访问性、原备注与次数。新入口只写新结构，旧数据和新数据分开统计。若以后执行批量迁移，按旧 ID 建唯一映射，先预演、再分批校验；保留原集合和新写入记录，出现差异时可切回兼容阅读。用户主动删除时单独处理归属与引用，避免删掉仍被历史条目引用的照片。

## 4. 交付顺序与通过条件

| 阶段 | 要交付的功能 | 通过条件 |
|---|---|---|
| M0　恢复旧版与真机验证 | 用微信开发者工具导入本仓库；在测试环境修复列表加载；做一个原生视频验证页 | 空集合进入空态，有记录能打开详情，新增后返回可见；测试账号之间无法读取对方数据。在华为 HarmonyOS 4.2 微信选择横屏、竖屏、30/60 FPS 视频，用可见时间标记核对跳转；记录设备、微信和基础库版本 |
| M1　去岩馆真正记一次 | 日历、计划、实际场次、线路选择、新建线路、单击添加尝试、体感、无视频记录、历史兼容 | 通过开头的“两天三次”场景；弱网重发同一次操作仍为三次；同日两场训练能分别查看；旧记录和照片可读；计划、旧汇总都不会抬高逐次统计 |
| M2　给一次尝试挂上视频 | 独立保存尝试，用户选择授权后上传，服务端校验文件；持久任务、演示报告、证据跳转、取消与清理 | 上传失败还能查看原尝试；未传完重开后提示恢复或重选；已提交任务离开小程序后可查。重启 worker 能恢复，取消后旧 worker 不能写回；通知失败仍可打开报告。演示报告清楚标记为模拟 |
| M3　接入真实视频分析 | 用可替换的视觉或姿态分析实现产出带时间的观察、原因假设和下一次建议；保留用户纠错 | 用经授权的真实样本覆盖 30/60 FPS、动态动作、遮挡和多人；人工核对所选人物、关键事件时间及建议对应的画面。身份不明或画面不足时给出限制或拒绝，供应商报错不进入建议正文 |
| M4　小范围使用 | 个人数据导出、视频保留选项、删除与过期处理；自愿岩友试用 | 岩友无需指导即可完成“记一次→回到这条线→查看报告”；实测过期对象无法再播放，清理涵盖失败、取消和衍生文件；核对每段处理费用和耗时，再决定开放范围 |

**依赖关系。** M0 的记录读写与权限通过后即可进入 M1。本地选片和播放可与日志开发并行。私有上传、取消和断网重开需要可用测试存储；这部分可单独验收，进入 M2 前必须补齐。M2 用虚构样例验证页面和任务；M3 再评估真实动作判断。深度双视频同步、社区、独立 App 排在上述范围之后。

## 5. 视频、隐私与 AI 的约定

- **默认只记日志。** 相册原件由用户保管。需要分析时按次授权上传，长期回放副本另行选择。临时文件到期后，历史记录明确显示“需重新选择原片”；已获授权保留的文字报告仍可查看。具体保留时长在存储和清理实测后确定。
- **时间以所上传的片段为准。** 报告存毫秒，播放器适配层负责单位转换。抽帧和裁剪保留与上传视频的时间映射，解码使用实际展示时间戳。用带时间标记的素材检验第 5 秒处的同一动作在 30/60 FPS 下均可找回。
- **授权覆盖整个处理过程。** 从业务身份校验场次、线路、尝试、视频和报告的归属。worker 领取任务、调用模型和写回前检查授权、删除状态与租约；访问私有视频使用短期授权。测试要包含用另一账号的资源 ID 尝试读取和写入。
- **建议能回看。** 报告中的观察带片段时间和证据引用，假设注明不确定性，建议指向下一次可以尝试的动作。长时间遮挡保留缺失标记。沿用蓝图的 `contracts/analysis-report.schema.json` 和 `core/domain.py` 检查报告结构、时间范围和引用，再用人工标注评估内容是否可信。

## 6. 第一个开发任务

**交付物为一个能在测试环境打开旧记录、在真机定位视频片段的开发版本。**

1. 导入含 `project.config.json` 的本仓库。核对实际云环境、开发权限、旧集合是否有个人数据及访问规则；对未知环境仅做只读核对。没有测试云环境时，先用测试数据验证页面，把云端读写标为待验。
2. 修 `pages/record-list/record-list.js`。当前初始 `loading: true`，而 `loadRecords()` 遇到该状态立即返回。统一首次进入与再次展示时的刷新入口，覆盖空列表、有数据、加载失败重试、第二页加载失败后重试四个场景。
3. 新建开发用 `pages/media-check/`，用自有测试素材操作“选片→预览→跳到第 5 秒”。有测试存储后补“私有上传→取消→断网→重新进入”；开发页随正式发布构建排除。
4. 记录开发者工具结果和真机结果，列出通过项、复现步骤、缺少的配置及下一项工作。若云环境满足权限和写入要求，下一次改动就做“开始场次→选择长期线路→连续记录两次尝试”。

本计划依据本地提交与同级蓝图编写。真实云环境、历史数据量、账号权限和真机表现仍需在 M0 核实；蓝图的验证记录仅覆盖其已有领域规则和契约。
