## 3. 关键设计与边界

### 3.1 预算与计量

- `PHOTO_SPACE_POLICY`：B = `100 MiB = 104857600` 字节，W = `80 MiB = 83886080`，R = `10 MiB = 10485760`；`1 MiB = 1024 × 1024`。是应用自设上限，不是平台/设备可用空间承诺。
- 逐项 `listMain` / `listThumb` 后对每个文件 `stat` 实际字节，不用索引里的写入时估值；同一 photoId 的主图 + 缩略图各计一次，跨天读取同一线路不重复计费。
- 孤儿文件与未完成操作文件照实计入；只有 `cleanupOrphans()` 证明无引用后才可删除。
- 提醒：`total >= W` 显示提醒；`total > B` 显示超预算。边界（低于/等于/高于）用注入小预算测试。

### 3.2 新增/更换峰值

- 顺序：压缩主图 → 压缩缩略图 → `stat` 两个临时文件实际字节 → 计量当前受管目录 → 检查 `当前占用 + 新主图 + 新缩略图 + R <= B` → 才写受管目录 → 提交索引。
- 更换时旧主图/缩略图仍在，峰值天然包含新旧共存；**不会先删旧照片制造空间**，成功提交后才清理旧文件。
- 预算不足返回 `space-insufficient`（可恢复），旧照片、索引、场次与尝试保持；实际 `copyFile`/压缩/索引写入报 `no space`、`ENOSPC`、`空间不足` 等同样归为该错误。
- 并发说明（**返工第一轮已修正，见第 9 节**）：首轮仅按“当前占用”判断，同一服务并发保存或串行重建可以各自按同一份未预留预算放行。返工后新增/更换/重建都会先登记在途预留，预算口径为 `实际占用 + 先到预留 + 本次新增 + R ≤ B`，先到先得、失败可重试、预留随操作释放。

### 3.3 普通清缓存

- 只删除 `thumb/photo-*.jpg` 与缩略图元数据键 `climbingNote.gymLogTrial.photoThumbs.v1`。
- 主图、`climbingNote.gymLogTrial.photos.v1`、场次/尝试缓存、模拟账本、其他缓存键与其他目录文件不动。
- 有照片操作进行中时页面与服务都拒绝清缓存。
- 清后列表缩略图回退主图路径；重开页面仍可读主图。缩略图重建覆盖当前数据集与重置后保留的旧数据集照片，避免缺失数无法归零。

### 3.4 重置与迟到回调

- 取消不改变场次、尝试、照片、索引或账本。
- 有照片时确认重置轮换 `datasetId`，旧照片/索引保留在旧数据集，不会挂到复用编号的新线路。
- 重置先重置账本、再写客户端；客户端写入失败时用 `restoreLedger()` 恢复原账本，原资料可重试。
- 照片控制器在数据集切换/清空时递增代次；旧操作回调按 `datasetId + generation + 当前操作对象` 校验，不写回新数据集视图、不提示“已保存”。
- 重置时新数据集服务初始化会中止旧数据集 `started` 操作并清理其半成品文件；受影响的旧页面得到失败而不是假成功。

### 3.5 缩略图重建

- `rebuildThumbnail` 仍按当前数据集公开校验；内部 `rebuildThumbnailRecord` 供清缓存后的批量重建使用。
- 开发者工具对 `http://usr` 持久路径调用 `wx.compressImage` 报 `file doesn't exist`，因此 `photo-files.compressImage` 在压缩器失败时回退离屏画布重绘；主图字节与关联不变。
- 缓存元数据宽度/高度改为实际缩略图尺寸（开发者工具证据为 320×240），不再记录主图尺寸。

### 10.1 阻塞项与修复

- **B01 预留释放写失败**：`photoReservations.v1` 的每条预留新增 `runtimeId/opId`。
  `recover()`、下一次 `claimReservation()` 都会按操作终态（failed/aborted/committed）
  回收残留预留；同一 `opId` 的新尝试取代该操作旧预留；仍为 `started` 的操作、
  其他运行期的活跃预留保留。故障解除后无需删除用户照片或放宽预算即可重试。
- **B02 异步 unlink 与同 opId 重试**：新增 `photoDeletes.v1` 删除声明。
  `cleanupOrphans()`/失败清理在真正 unlink 前登记 `{photoId, runtimeId, instanceId}`，
  异步边界后按最新索引、进行中操作、在途预留再次复查；保存/重建遇到声明返回
  可恢复的 `cleanup-in-progress`，不写入或提交。旧运行期遗留声明由下一次
  `recover()` 立即失效。旧 unlink 完成后同一 `opId` 重试成功，最终主图存在且索引一致。
- **B03-a 租约写失败**：`reserveForWrite()` 先刷新租约，写不进去返回可恢复的
  `coordination-failed`，不再进入主图/缩略图写入；故障解除后可重试。
- **B03-b 活跃操作超 TTL**：模块加载生成 `runtimeId`，同一运行期所有服务实例共享；
  `recover()` 只中止其他运行期的 `started` 操作，同一运行期其他实例（含其他
  owner/dataset）的后台暂停、长 await 即使超过 5 分钟租约也保留。无 `runtimeId`
  的旧版记录才退回租约 TTL。
- **B03-c 真实重启**：新运行期（新进程/小程序重启）得到新 `runtimeId`，
  `recover()` 在 TTL 内立即中止遗留保存、回收其租约/预留并清理半成品；同一
  `opId` 可立即重试。新服务实例本身不等同于新运行期。
- **重置/切换数据集**：`openTrialPhotos()` 在数据集变化时调用
  `abandonStartedOperations()`，只放弃旧数据集自己的未完成操作；正常 `recover()`
  不调用它。
